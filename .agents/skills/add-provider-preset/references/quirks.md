# Quirk interview and decision aid

Use this when authoring a preset, after researching its endpoints and model docs. Work through **each configured target independently** and then each documented model exception. Show the user a proposed disposition for every applicable field and ask them to confirm or correct it; ask focused questions where research leaves a gap. Small conversational batches are fine, but don't skip applicable rows. Give the specific doc URL/section or a redacted request/response example next to every proposed capability. Say "unknown" when the source is silent. Unknown is not `false`, not a provider default, and not permission to add a guessed map.

## Pick the quirk source

- Prefer `piAiProvider` when the actual upstream model IDs can be looked up under the intended pi-ai catalog provider. Verify the provider key and relevant models, not just a similar provider's name. This uses the catalog model's API, reasoning map, limits and compat traits, not the inline quirk fields. Auto-compat runs only with `autoCompat: true` and a configured model's `pi_ai_model_id` resolving under that provider; unresolved or unmapped models get no catalog projection. Ask: "Do these exact model IDs map to this pi-ai provider, or do you use gateway-specific IDs?" A matching-looking gateway isn't proof that its dialect or model capabilities match the builtin provider.
- Compare the catalog model's `api` with every configured endpoint where that model can route. The runtime uses the builtin record's `api` for its outbound projection, even when the selected target is another protocol. A real builtin with Messages-only model records does not establish safe Chat auto-compat; verify the resulting request shape or keep it off.
- Use `piAiQuirks` instead when verified provider/target behavior can't be represented by that builtin lookup. `piAiProvider` and `piAiQuirks` are mutually exclusive. Quirks are indexed by target and inline `models` keys match the **exact upstream route model ID** (`route.model`), not a display label, alias guess or `pi_ai_model_id`. The preset can only declare quirk targets also present in `apiBaseUrl`.
- `autoCompat` defaults to false and requires one of those two sources when true. Inline quirks with auto-compat off don't project requests. An inline API declaration alone doesn't imply any model capability: if no applicable declared trait produces options, the payload stays unchanged. Non-quirk targets such as embeddings, transcription and speech can have endpoints without inline quirk entries. Do not invent entries to make every endpoint look covered.

Allowed **inline target → fixed `api` dialect** (no other keys or dialects):

| `piAiQuirks` target | Required `api` value | Outbound projection |
| --- | --- | --- |
| `chat`, `completions` | `openai-completions` | OpenAI chat-completions-shaped fields |
| `responses` | `openai-responses` | OpenAI Responses-shaped fields |
| `messages` | `anthropic-messages` | Anthropic Messages-shaped fields |
| `gemini` | `google-generative-ai` | Gemini `generationConfig` fields |

For each configured target, ask: "Is this endpoint actually the listed dialect? Which upstream doc or captured request demonstrates it? Does the same model behave differently on another target?" `chat` and `completions` have separate target entries even though they share one `api` value. The schema restricts these pairs; a claimed `chat` endpoint with a different dialect needs a corrected target or explicit clarification, not a changed `api` literal.

## Ask per target and model

Keep a compact evidence ledger: target, exact model IDs covered, claimed value, doc URL/section or redacted example, and status (verified / contradicted / unknown). A single model's docs don't establish a provider-wide default. Use target-level traits only when evidence covers all models intended to inherit them; put exceptions in `models[exactUpstreamModelId]`. If the model set is open-ended, leave unverified traits out of the common entry and set them only on evidenced models. Where docs are silent, ask the user for a known working or rejected payload, then for confirmation; if still unknown, omit the trait or explain why the requested transformation cannot be safely enabled.

- `reasoning` (optional boolean). Ask: "Does this model support reasoning on **this target**? What docs or successful/failed thinking request confirm yes or no?" `true` only with positive evidence; `false` only with evidence the model doesn't reason, not silence. For inline projection, `reasoning: true` needs `thinkingLevelMap` on the resolved target/model. A map at target level requires target `reasoning: true`; a model-level map requires the resolved model `reasoning: true`. A model-specific `reasoning: false` removes an inherited map at runtime. No client reasoning intent means don't force the model to off.
- `thinkingLevelMap` (optional per target/model). Ask: "For explicit off and each relevant client level (`minimal`, `low`, `medium`, `high`, `xhigh`, `max`), what's supported on this protocol? What exact provider value does the documentation name for each supported level?" Only these keys (and `off`) are accepted; values are string or `null`. Don't guess an identity mapping. A string records the provider value, though not every protocol copies that string directly into its outbound payload; the map also guides pi-ai's level clamping. `off: null` means reasoning cannot be disabled: explicit off clamps to a supported level if one exists, otherwise the runtime emits no thinking option. An off string names a verified provider value. Omitted `off` does **not** prove on/off support either way; inline dispatch won't project explicit off without an `off` key. Null on another level marks it unsupported, while omission leaves it unestablished.
  - Gemini: concrete `minimal`/`low`/`medium`/`high`/`xhigh` map entries select level-based `thinkingConfig.thinkingLevel`; without them the enabled reasoning path sends budget-based `thinkingConfig.thinkingBudget`. Ask which wire form the model accepts.
  - Anthropic: ask separately about adaptive effort versus token-budget thinking (below); dispatch builds these fields rather than copying map strings onto the wire.
- `maxTokens` (optional positive integer). Ask: "What's the **maximum output tokens**, not context window, for this model and target? Which published limit or observed over-limit response supports it?" The runtime clamps a client-requested output limit to this ceiling; absence doesn't license a fabricated number. Inline dispatch only selects max-token projection when this field or `compat.maxTokensField` is declared. Protocol output fields differ: completions `max_tokens` or `max_completion_tokens`, responses `max_output_tokens`, messages `max_tokens`, Gemini `generationConfig.maxOutputTokens`.
- `compat.supportsTemperature` (optional boolean). Ask: "Does this model/target accept an explicit `temperature`, and does it still accept one with thinking on? Show an accepted request or a documented rejection." `false` drops a supplied temperature; `true` allows it through the model guard, except Anthropic thinking-on drops it regardless. Omit when unknown rather than asserting support or rejection. Inline dispatch only selects temperature projection if this trait is declared.
- `compat.maxTokensField` (optional `max_tokens` / `max_completion_tokens`). For `chat`/`completions`, ask: "Which of those **request field names** does this endpoint accept for this model?" `max_completion_tokens` rewrites the output-limit field; `max_tokens` uses the normal one. Declaring either also opts inline dispatch into output-limit projection. This selector is not a Responses, Anthropic or Gemini field-name switch; use their projection fields above.
- `compat.forceAdaptiveThinking` (optional boolean). Only useful for `messages`. Ask: "Does this model accept `thinking: {type: 'adaptive'}` and optional `output_config.effort`, or require `thinking: {type: 'enabled', budget_tokens: ...}`? Is an explicit off request supported?" When true, runtime emits adaptive thinking and effort when supplied, otherwise it uses budget-token thinking. The explicit `off: null` case clamps toward supported thinking rather than sending disabled. Don't set `true` merely because the model reasons; omit on other protocols.
- `compat.supportsReasoningEffort` (optional boolean). Only relevant to OpenAI-completions projection. Ask: "Does this target accept top-level `reasoning_effort` for this model, in addition to (or instead of) its provider thinking field? Which values?" True lets `zai`, `deepseek`, `together`, and native/default completion projection write a mapped effort; false makes the native/default branch strip unsupported effort. Unknown is **not** false: the native/default branch can pass through an existing client `reasoning_effort` when it is itself the intent and no conflicting reasoning object was removed. For inline completions, this trait's **presence** (either boolean) also opts into reasoning projection when a map exists. It doesn't change Responses, Anthropic or Gemini projection.

### `compat.thinkingFormat` on `chat` / `completions`

Ask: "Which **request shape** does this endpoint expect for enabling/disabling thinking? Please link the payload docs or provide a redacted accepted request for on, off, and effort." This is optional and only consulted by the OpenAI-completions projection. Distinguish API dialect from provider branding. Allowed enum values and actual outbound behavior:

| Value | Enable / disable wire form | Effort handling |
| --- | --- | --- |
| `zai` | `thinking: {type: 'enabled', clear_thinking: false}` / `{type: 'disabled'}` | Optional top-level `reasoning_effort` if `supportsReasoningEffort` and mapped effort. |
| `qwen` | `enable_thinking: true` / `false` | No separate mapped effort emitted. |
| `qwen-chat-template` | `chat_template_kwargs: {enable_thinking: true/false, preserve_thinking: true}` | No separate mapped effort emitted. |
| `deepseek` | `thinking: {type: 'enabled'}` / `{type: 'disabled'}` | Optional top-level `reasoning_effort` if opted in and mapped. |
| `openrouter` | `reasoning: {effort: <mapped>}` / `{effort: <off string or 'none'>}` | Replaces a client reasoning object; removes stale top-level `reasoning_effort`. |
| `ant-ling` | `reasoning: {effort: <mapped>}` on enable | Off or unexpressible intent removes both reasoning notations rather than sending a disable value. |
| `together` | `reasoning: {enabled: true/false}` | Optional top-level `reasoning_effort` when enabled and opted in. |
| `string-thinking` | `thinking: <mapped string>` / `<off string or 'none'>` | Provider string, not an object. |

Without a `thinkingFormat`, the native/default OpenAI-completions path may use `reasoning_effort` when supported; don't pretend an unlisted wire format exists. `chat-template` appears in the dispatch switch for builtin catalog models but is **not allowed** by the inline schema. These format choices do not change the Responses `reasoning` object, Anthropic `thinking` object, or Gemini `thinkingConfig`. If the docs show another shape, ask rather than force it into the closest enum.

Model override inheritance matters: `models[ID]` inherits target `api` and unoverridden top-level traits; its `compat` object merges property-by-property with the target's `compat`, but a model's `thinkingLevelMap` replaces the entire common map, **not** individual levels. Restate the effective values for each exception before asking for confirmation, including any inherited off behavior. A model with no exact ID match inherits target traits.
